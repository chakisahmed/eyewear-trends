# Eyewear Trend Intelligence: Build Plan

## Context
From the handwritten note: an **AI-powered app that tracks the latest eyewear trends**. It covers aesthetics, demand and fashion, broken down by **frame form (shape) and colors**, and shows the results on a **dashboard**. Data comes from **blogs, articles, eyewear stores and social media posts**. The idea and the prompt can still be expanded later.

- **One eyewear retailer uses the app (single tenant):** Noé & Noah. It is an internal tool for their buying and merchandising team.
- **French is the primary language.** The UI, AI summaries and reports are in French. Sources and search queries are **both French and English**.
- It is a real product. The stack is a Python API (FastAPI) with a Next.js frontend.
- The LLM sits behind a provider interface (`app/extraction/llm.py`). The default implementation uses the Anthropic SDK with `claude-sonnet-5`.

## Core idea: how the pipeline works
```
Collect (FR+EN) -> Extract (LLM) -> Normalize to taxonomy -> Score trends -> Dashboard (FR)
```
The key design choice is a **fixed, language-neutral taxonomy** (`backend/app/taxonomy/taxonomy.yaml`). The LLM reads French or English text and can only answer with its codes, which structured output enforces through Literal enums. The UI shows French labels, so "lunettes œil de chat" and "cat-eye glasses" count as the same trend. Each entry also carries bilingual search keywords.

```
  extraction/      llm.py (provider interface), schema.py (generated from taxonomy), service.py, prompts/ (versioned)
  scoring/         trends.py (weekly momentum + status), summary.py (French weekly summary)
  api/main.py      FastAPI routes (overview, trends, demand, mentions, sources, demo, CSV export, jobs)
  jobs/            pipeline.py (recorded as JobRun, live step progress), scheduler.py (daily 06:00 Europe/Paris)
  collectors/stores/  Phase 2 store catalogs: store_configs.yaml (one entry per domain, CSS-only rules),
                   config.py, parser.py (JSON-LD first, CSS fallback), base.py (async crawler), tagger.py
                   (rule-based taxonomy tags) - none of these touch the DB or an LLM; service.py persists
  migrations/      Alembic, applied automatically at startup
  demo.py, cli.py  click CLI: run, backfill, refresh-search, crawl-store, retag-products, seed-demo, clear-demo

                   hand-written SVG charts with table views. See docs/ui-plan.md and docs/design-brief.md

```
**Database:** SQLite by default, Postgres in docker-compose. Tables:
- `sources`
- `documents`
- `products` (store catalog items, upserted by url)
- `product_tags` (product → taxonomy code links from the rule-based tagger, with provenance; color tags carry three tiers: `color_family` (Palier 1), `color_hex` (Palier 2, from the taxonomy) and `supplier_code` (Palier 3, a store's own variant code, from the crawler and never stored in the YAML))
- `mentions` (the evidence behind every trend)
- `search_interest`
- `trend_snapshots`
- `job_runs`
- `weekly_summaries`

Foreign keys: `documents` → `sources`, `products` → `sources`, `product_tags` → `products`, `mentions` → `documents`. The trend tables are joined on `(dimension, code)` in code.

**Sources:**
- **Feeds:** 17 RSS feeds. Trade press: Optique Mag, Vision Monday, Invision. FR and EN fashion media: Vogue, GQ, Grazia, M Le Monde, WWD, Hypebeast and others.
- **News:** GDELT news queries, best effort (rate-limited on the current network).
- **Search:** Google Trends for France.
- **Sitemap press:** Acuité (French optical trade press, no RSS), collected daily from its XML sitemap (`sitemap_news.py`). Only `/actualites/lunettes/`, with a 7-day window on each article's own date, at most 10 new articles per run.
- **Stores:** Outika (outika-eyewear.tn), MyKenza (mykenza.tn, sunglasses) and LaMode (lamode.tn, designer prescription frames), all Tunisia, via `crawl-store`, run manually. Free: no LLM. Plus Etnia Barcelona (etniabarcelona.com, Spain), the first creator-brand catalog. The "Marché Tunisien" shelf and its gaps count Tunisian stores only (`retail.MARKET_COUNTRY`); trend pages' "Présence en boutique" shows every store, prices per currency.
- **Archives:** a one-off backfill of the trade press from sitemaps and paged feeds. It only collects, and the CLI prints the Claude cost of analysing what it collected before anything is spent.

**Trend score:**
- **Volume:** the sum of source weights over the week's mentions.
- **Momentum:** growth versus the previous 4-week average, blended 30 % with Google Trends growth.
- **Tone:** the balance of rising versus declining mentions, pooled over 4 weeks.
- **Statuses:**
  - `en_hausse`: rising.
  - `au_pic`: the 4-week least-squares slope flattens after a sustained rise.
  - `stable`
  - `en_baisse`: momentum ≤ −25 %, or at least half of the mentions describe the look as fading.
  - `faible` ("Peu de données"): fewer than 5 weighted mentions in 4 weeks. It overrides every other status.
- **Summary:** it only calls out trends backed by enough data. Weak signals are listed as "à surveiller".

Crawling modules have no DB or LLM imports; an AST test enforces this.
  - Step 2 (done): Outika config and the `crawl-store` CLI. First live crawl: 222 products. Data-quality fixes: a price ≤ 0 counts as missing (Outika publishes 0.00 for sold-out items), stock status comes from the page and not the JSON-LD (which says "InStock" for sold-out items), categories captured, empty flags stored as SQL NULL.

  - Step 4 (in progress): second store, MyKenza (mykenza.tn), a multi-brand store (Ray-Ban, Loewe…). Shapes come from its JSON-LD description ("Forme : Oeil de Chat – Style : … – Matière du cadre : …"), which the new opt-in `description_specs` reads into `raw_specs`. Three general parser additions came with it:
    - the price is read from `offers.priceSpecification` (the sale price, not the ListPrice),
    - `@id` references in the JSON-LD graph are resolved (Yoast's `"image": {"@id": …}`),
    - lazy-load `data:` placeholder images are ignored.

    Tagger rules v2: frame-material and gender spec labels, plus store vocabulary aliases in specs only (acier/inox → metal, carey → tortoiseshell). `taxonomy.yaml` is untouched.
  - Step 5 (discount signal): `products.list_price` (migration 76b043af5674), read from JSON-LD `priceSpecification` (ListPrice / StrikethroughPrice) or a CSS rule, always from the same source as the selling price, and kept only when above it. Markdown is read **relative to each store's usual markdown** (MyKenza runs a store-wide -25 to -50 % sale). Stores without list prices are excluded. A declining attribute discounted at least 10 pts deeper than usual is a "déstockage" stock risk. Shown on the trend detail page (`retail_markdown`), in the report and in the weekly summary's input.

  - Step 7 (3-tier colors, migration a41c7d9e2b56, tagger rules v5): color tags carry family, hex and an optional supplier/variant code. A crawler that exposes variants writes `flags["variants"] = [{"code": "HV/BL", "color": "Havana"}, …]`; each label the tagger recognises gives one tag per code, so two codes of one family coexist. Uniqueness is `(product, dimension, code, supplier_code)` plus a partial unique index for uncoded tags (SQL treats NULLs as distinct). Existing tags were backfilled by `retag-products`; no store exposed variant codes yet.
  - Step 8 (first creator brand: Etnia Barcelona, Shopify, ~684 frames, EUR; tagger rules v6). Model names (KORE, IZZI) carry no shape, and the product-page shape metafield was absent from every sampled page, so shape, gender and material come from the store's own listing filters. Four generic crawler additions, all driven by `store_configs.yaml`:
    - **Facet passes** (`listing.facets`): the filter's values and labels are read from the listing's filter form, then the collection is listed once per value, **one filter per request** (robots.txt forbids combined filters, a rule Python's robotparser does not apply), and the label goes into `raw_specs`.
    - **Canonical URLs** (`listing.url_regex`): `/collections/sun/products/izzi?variant=…` → `/products/izzi`, one product per frame.
    - **Per-listing categories** (`{url, categories: "Solaire"}`) for product type.
    - **Color variants** (`variants`): each swatch's commercial code (Palier 3, verbatim) and the store's own color name, which the tagger maps to a family. No code is decoded; "Blue", "Orange"… stay untagged until the taxonomy step.

    Also: listing and product-page `raw_specs` are merged instead of the page's replacing the listing's; query strings encode spaces as `%20`, never `+`. Product `.json` is not fetched (it lacks color names). Rules v6: "PANTOS SQUARE" → square and "CAT-EYE/BUTTERFLY" → cat_eye, one shape each.
  - Step 9 (color families v2, prompt v2, tagger rules v7): 8 new Palier 1 families (blue, red / burgundy, green / khaki, grey, white / ivory, pink / fuchsia, purple / aubergine, orange / yellow). `bold` stays but narrows to **Multicolore** (multicolour, neon, no named hue), flagged `multicolor` in the taxonomy and drawn as a spectrum. No code was removed, so no stored row points to an unknown code. Why: constrained to the old codes, the LLM had silently dropped colours ("available in khaki, blue and black" stored as black only: 49 of 146 colour quotes), and 24 of Etnia's 37 colour names had no family. `reread-colors` re-reads past articles for colours only (other dimensions keep their first analysis; prints its cost; `--confirm` spends, 100 per run, resumable). The 2026-07-06 snapshot week sits outside the 12-week rescore window and keeps its old colour rows.
  - Step 10 (summary prompt v3, colour guaranteed): color is a stakeholder focus ("Studio de Coloration"), so it may no longer lose every bullet to shapes. The brief lists the colour families that must be cited (≥ 10 mentions over 4 weeks, en hausse or au pic, strongest first; zero LLM), `summary_fr_v3.md` requires one bullet dedicated to one of them, named as in the taxonomy, and a warning is logged when the text names none. The summary prompt is versioned on its own (`summary_prompt_version`), so bumping it never makes article extractions look outdated. The articles' one-line `summary_fr` extracts are deliberately left from their first analysis (not re-read).
  - Step 11 (laminations and best-sellers, tagger rules v8; plan: `docs/phase2-step11-laminations-bestsellers-plan.md`). Etnia's swatch names only the main colour; its try-on widget JSON names every acetate layer ("Havana/Blue", matched to swatch code HV/BL by frameId), read by the opt-in `variants.layers: vto_carousel`. A multi-layer variant gets a colour tag per layer, Bicolore (`two_tone`), and a non-taxonomy `lamination` tag ("blue+tortoiseshell", order-free), all with the variant code; a layer with no family (Zebra) is never guessed into a combination. Best-sellers come from the store's own filter via a flag facet (`only: ["Yes"], flag: is_bestseller`): True for listed frames, False for the rest only when every page loaded, otherwise unknown. Frame level only: which colour sells cannot be read reliably. Shown as a "Best-seller" pill and count in "Présence en boutique".

  - Step 13 (frequent pairings on colour pages). `retail.color_pairings` aggregates the `lamination` tags of active frames into the partner colours of a colour (`blue` with `tortoiseshell` 97 frames, `black` 47…), counted in frames (a frame with several codes, or a three-layer lamination, counts once per partner), best-sellers taken from the store's own frame-level flag. `GET /api/trends/color/{code}` returns it as `pairings` (top 8 partners, `null` when no frame shows the colour or on other dimensions); the colour detail page shows an "Associations fréquentes" block: a bar per pairing in the partner's real colour, a coral edge and the Best-seller pill (count, rate, up to two example frames) where the pairing includes best-selling frames.
  - Step 14 (catalog history; plan: `docs/phase2-step14-catalog-history-plan.md`). Part 1: `products` gets `first_seen_at` (set once), `is_active` and `dropped_at`, backfilled from `seen_at` and the old 14-day rule (migration `c5e8b13f7a90`, applied live: 1,471 products, all active). Part 2: `StoreSyncService.sync(source_id, products, report, accept_drops)` keeps them true. The crawler now records a `CrawlReport` (`crawler.report`): every URL its listings returned (in stored form, so a card that fails validation is still "listed") and the reasons the listing may be incomplete (a page that failed or was refused, an empty page behind a `next` link, stopping at `max_pages` with more to list; facet-pass failures do not count). A product is dropped only if the crawl was complete AND the listing holds at least 70 % of the store's active products (`--accept-drops` waives only the second guard); a returning product is reactivated; `seen_at` of a dropped product is never advanced; a re-run changes nothing. `retail.active_products` now reads `is_active` (the 14-day window is gone). `crawl-store` prints reactivated/dropped and why drops were skipped. Part 3: `python -m app.cli crawl-stores [DOMAIN...] [--force] [--dry-run]` for **Windows Task Scheduler** (`tools/crawl-stores.cmd`, setup in `docs/crawl-stores-task-scheduler.md`; the app's own scheduler is not used). Every crawl is a row in the new `store_crawls` table (migration `d7a3c94e1b28`, live). A store is due when its last complete crawl is older than `crawl_every_days` (default 7, minus 12 h slack); an incomplete or failed crawl is retried after 20 h; a crawl killed mid-way is marked interrupted and does not delay the retry. Stores run one after another, one failing never stops the others, each capped at 3 h; an OS file lock allows one crawl process at a time; running twice in a row crawls nothing the second time. Exit codes: 0 fine or nothing due, 1 a store failed, 2 a crawl was incomplete or skipped its drops. `crawl-store` shares the runner, is logged as `single`, and now exits 1 if the crawl failed. Part 4, the read side (`scoring/catalog.py`, no migration): a store's history starts at its first complete (`ok`) crawl in `store_crawls` (its baseline; products known before it, including hand-crawled ones, are baseline and never "new"). **New** = first seen after the baseline within 30 days; **retired** = dropped by a complete crawl within 30 days and not back. Trend pages get `retail_new_count`, `retail_retired_count` and a "Nouveauté" pill (the sample keeps up to 2 slots for in-stock new frames, since a store with many best-sellers would otherwise hide them). `GET /api/catalogs` feeds a "Catalogues et boutiques suivis" panel on the Sources page: per store the active products, new and retired, the age of the last complete crawl and a state (À jour, En retard past 2 x cadence, Incomplète, Échec, Collecte manuelle), plus what **creator brands** (stores outside `MARKET_COUNTRY`) added by attribute, with shares only from 10 new frames. The weekly brief gets the same creator-brand section and the summary prompt becomes v4 (one bullet on the gap between the share of new frames and of the catalog; the mandatory colour bullet is untouched).
  - Step 14, part 5 (what the first live `crawl-stores` run taught us, 2026-09-29). MyKenza came back `incomplete` (`max_pages` 10 cut both categories: 168 of 190 read, nothing dropped, as designed): now 20. LaMode's first page timed out with an empty log line: `fetch` now retries transient failures (timeouts, connection errors, HTTP 429/500/502/503/504) twice after 5 s and 15 s (a `Retry-After` wins, capped at 60 s), never retries a real answer (404, 403, robots.txt), and logs the exception name. Etnia had two facet pages answer 503: a crawl replaces a product's flags wholesale, so a failed facet page would have erased known values (material Metal, `is_bestseller`, a variant's colour). Now the crawler records each such page as a `FacetGap` in the `CrawlReport`; `carry_over` keeps the previous value for exactly that slice (only if the old value had it and this crawl has none), counted as `carried`; and a crawl with gaps is `incomplete` (retried after 20 h, exit code 2, the gap line in `store_crawls.problems` and on the Sources panel) while its drops are unaffected, since presence never depends on facets.

Marketing colour names are not guessed: aliases come from the first crawl's report.

## Decisions
- **Retailer country: Tunisia.** French stays the UI language. The Google Trends geo stays `FR` (`market_geo`) as a proxy.
